# switchyard

Host-detected Git control tampering carries only the closed `gitControlTamper {kind, area}` tuple through the result, run record, routing attempt and failure log; raw paths and messages stay out of those records. To keep a stray write from costing the whole run, every provider prompt forbids git writes and `.git` edits, and the native launcher Seatbelt profile (Claude Code, Vibe Code) denies writes to `.git` itself, `config`, `hooks`, `info` (except `info/refs`), `objects/info` (except `packs`) and `refs/replace` while the index, objects, refs and logs stay writable. The keyless bridge (OpenCode Go, Vibe), Agy and Copilot are detect-only; Codex's `workspace-write` sandbox already denies all of `.git`.

A containment-first Node.js dispatcher that routes coding tasks across subscription-backed agent CLIs. Ordinary bounded changes use run-scoped routing across eligible tier 1 and tier 2 providers in disposable local Git clones with a strict file allowlist and the provider's own workspace sandbox. `switchyard-dispatch simple` is the only dispatch path: the owner retired the Parallels VM, persistent queue and detached dispatch family on 2026-10-18 (audit decision O1). Threat model: **accident-containment, not adversary defense**. One known gap sits inside that model: any process Switchyard confines with Seatbelt can read the argv and environment of every other same-user, non-platform process on the host through `sysctl` `KERN_PROCARGS2`, including children of `bws-secret-exec` that hold secrets in their environment. Seatbelt does not mediate that read, so no profile closes it while toolchains still run; only a separate account would, which the owner declined on 2026-10-19. For a Quick check the value stays on the host: checks have no network and repair prompts never carry check output, but a failing check can leave it in its owner-only `check-evidence` log, where credential-shaped redaction is not guaranteed to catch it. A provider run is not so contained, because whatever a provider reads can reach its model endpoint: the same read goes through under Switchyard's own native launcher profile for Claude Code and Vibe and under Codex's Seatbelt sandbox (default and `workspace-write`), both verified on 2026-10-19; the other harness sandboxes are unverified. `tests/runner-quick-checks-sandbox-procargs.test.mjs` tracks the check side as a `todo`.

**Dispatch path:** `switchyard-dispatch simple` runs bounded attempts in disposable local clones, checks each diff locally, and applies only declared files through the existing integration gate. Captains coordinating multiple tasks in one delivery MUST pass the same `--routing-run-id` for every task. If neither that flag nor `SWITCHYARD_ROUTING_RUN_ID` is supplied, standalone use generates a fresh ID for that invocation only and emits this warning: `dispatch: simple generated a standalone routing ID; use --routing-run-id or SWITCHYARD_ROUTING_RUN_ID to share failure memory across tasks.` The result envelope records `routingRunIdSource` as `flag`, `environment`, or `generated`, so callers can distinguish explicit shared state from the isolated generated ID. State is stored under the project's normal `getStateRoot()/routing-runs` directory. Failed target identities are excluded for the rest of that project/run, while successful targets remain available to later tasks until usage or another eligibility gate blocks them. Captains should leave provider selection automatic and unpinned. Use `--only-provider` only when the user or task contract requires an exact target; a pin narrows the eligible set and may bypass other tier 1 or tier 2 options. The caller exhausts eligible tier 1 by pace (furthest ahead of pace first, roster order on ties), then eligible tier 2 by headroom, before the task's exact authorized native fallback; the CLI routing envelope exposes `exhaustionCause` (`capacity` vs `task_failures`) for fallback authority. Red baseline checks stop as `baseline_failed` and a check environment that could not be set up stops as `check_setup_failed` (the JSON `stopReason`), while cleanup, cancellation, input, lock and run-store failures stop as `unsafe_failure` (a caller `--estimate-minutes` that cannot fit the time left stops as `task_estimate_exceeds_budget`; after a failed attempt the stop keeps that attempt's own reason and adds `retrySkipped`, and retained partial worktrees appear as `retainedPartials`); soft provider/check, empty-diff, environment and policy failures move to the next eligible target for ordinary tasks, up to four failed attempts. When the result describes a retry (for example a `deferred` `native_required` after the first target exhausted its quota mid-task), `priorAttempts` summarizes this task's earlier attempts in order: `attemptId`, `targetId`, `terminal`, `reason`, the engine's closed `failureReason` and `causeCode` (or `null`), and `partialWorktree` while that partial is still retained (else `null`). It is omitted for a single attempt, and every existing field keeps its meaning. After the authorized native child actually starts, the caller records its actual-start receipt and latches the run to native; subsequent tasks in that run make zero Switchyard provider calls. The latch does not authorize later work: each native task needs its own exact authorization manifest and route. The local adapters cover Codex, Antigravity Gemini, Antigravity Claude, Copilot Student, Vibe low and standard, and OpenCode Go low and standard through fixed keyless bridges; Claude Code runs natively on its own subscription login under a Seatbelt profile and is used only when pinned with `--only-provider claude-code`; the two Antigravity targets share the `agy` harness but retain distinct owner-selected model contracts. Capability, active descriptor, subscription or quota funding, adapter, scope, writer-stop, and cleanup gates remain binding. OpenCode Go additionally requires a fresh, distinct Go usage snapshot with at least 5% remaining in every tracked window; `roster.json` is unchanged.

The CLI binds each task to its canonical project and origin, using either `--task-id` or a digest of the prompt bytes and stable behavior scope (excluding transport artifact paths such as `predecessorReceiptPath`). The binding ignores the routing-run ID, deadline, prompt filename, and provider pin; keep the same `--task-id` when revised task text should resume the same identity. While generated routing IDs isolate run-level state across unrelated invocations, retrying the same task identity still links to its previous run whenever earlier attempts left failed, in-flight, native-latched, pending, or retained-partial state, stopping before provider allocation and returning `previousRoutingRunId`. A success-only task may start under a new routing-run ID; task-local failure memory remains sticky, and work and qualification identities stay separate. Stored task metadata includes only exact finite fields (schema version, canonical project path, origin, task identity hash, routing run ID, status `in_flight`/`failed`/`succeeded`, and the `hadFailure` flag); prompts, task text, outputs, and credentials are never stored.

Routing-run and task-binding locks use owner PIDs checked against the local process namespace. Keep their `stateRoot` on one host and PID namespace; do not share it across hosts or PID namespaces. Locks are reclaimed only when the owner is proven dead there. Live or indeterminate owners, malformed lock or claim data, unsafe paths, and ownership replaced during claim or release remain fail-closed. If both lock releases fail during cleanup, the earlier pending exception is preserved.

The low-level exported `runSimpleTask` remains a single selected-provider attempt; the command-facing routing-run wrapper owns the cross-task tier 1/tier 2 waterfall. Routing-run state records attempts and failed target IDs, and native mode is acknowledged only with a receipt proving the exact authorized native child actually started. Simple terminal results retain the compatibility `partialWorktree` field and add a content-free `recovery` envelope. It binds the task and attempt IDs, committed base revision, declared file scope, check digests, terminal status, partial-worktree path, and observed writer/worktree/project-lock cleanup. Continuation is available only when the partial checkout is retained, the writer is affirmatively stopped or never started, and lock release is confirmed; missing, drifted, or interrupted evidence remains unavailable. The envelope is caller evidence only: it is not a checkpoint, headless receipt, or proof of external/provider acceptance. Terminal simple JSON exposes the same sanitized closed `failureDetails` object as `run.json`. Successful provider execution with no diff is now reported and durably persisted as the typed `empty_diff` failure. Baseline failures stop without replay, hard failures stop as unsafe, and other typed failures retry the next eligible target within the four-attempt soft budget for ordinary tasks; pinned or high-capability tasks stop on the first soft failure.

Failed baseline, acceptance and repair checks expose only their actual redacted evidence path in terminal and durable failure details; provider failures keep their own artifact. Running simple status includes task identity, deadline, validated descriptor and observed process phase; heartbeat persistence stays throttled to 30 seconds, and terminal status clears active projections.

Simple tasks accept `--origin work|qualification` (default `work`); provider qualification supplies `qualification`. Qualification attempts preserve lifecycle safety checks but do not claim work health trials or affect work suppression. Failure summaries default to work, legacy records default to work, and diagnostic callers can select qualification or all origins.

Simple routing inspection adds version-1 accountability projections without changing persisted routing state. Verified provider diagnostics alone make new typed failures eligible for run-scoped provider memory; environment, contract, check-system, caller, cleanup and unknown failures do not. Legacy untyped callers keep their previous behavior. Immediate retry exclusion prevents loops while leaving unknown failures available to later tasks, and environment failures stop without automatic replay. A new routing call keeps one logical task ID across its attempts. `routing-run inspect` reads identity-verified linked run records to report attempt and unique-task success totals per provider; missing or mismatched records are unknown. Applied success and cleanup failure are reported independently. Every failed attempt and every non-complete stop is also appended to `<stateRoot>/failure-log/failures.jsonl` with allowlisted fields only (never prompts, output, argv, environment or check commands); `routing-run failures [--since <RFC3339>] [--json]` summarizes it by fingerprint, target and reason for periodic tuning. Attempt and stop records also carry the engine's specific `failureReason` and, for a check-setup refusal, its `checkSetupStep`, `checkSetupErrorCode` and `checkSetupExecutable`, so a check-setup stop (`check_setup_failed`, whose attempt keeps the coarse `baseline_failed`) still names its cause. In `run.json` itself a cause code the previous release does not know, such as `check_setup_failed`, is written as the stand-in `unknown` in `lastFailure.providerReliability` because release `d48047a` is the rollback floor and its reader accepts only its own closed codes; the precise code is in `failureDetails.causeCode`, and `readRun`, which every Switchyard reader uses, restores it. Read run records through `readRun` rather than parsing `run.json` raw. A check the checker sandbox denied adds the `sandboxDeniedPath` its own output named. A refused diff's attempt record carries its `diffRejectionRule`, and for `integration_state_unknown` the `diffRejectionUnknownStep` and `diffRejectionUnknownCause` that name the `git apply` metadata step that failed. Its `--since` filter requires an explicit RFC3339 date-time and rejects invalid Gregorian dates and out-of-range clock fields while preserving the existing case-insensitive separator and numeric-offset syntax. A nonzero fractional remainder beyond milliseconds excludes events in the truncated millisecond. Shared validation also covers deadlines, failure-summary filters, failure-log lower bounds and outcome events; persisted routing timestamps remain canonical millisecond UTC, while retained-worktree `retainedAt` values use RFC3339 date-times with numeric offsets and fractional seconds in both historical and current run schemas. After the captain salvages or discards a retained partial, `routing-run release-partial --task-id <id> [--discard]` clears it so the routing run can continue (`<id>` is the `--task-id` you gave `simple`, resolved for the project under both origins the way `simple` binds it, or the persisted task hash that `routing-run inspect` shows); it verifies the worktree claim and refuses symlinks, a held project lock or ambiguous cleanup. A supported operator cancel is available next to it: `simple cancel --project <path> --run-id <id> [--timeout-seconds <n>]` re-reads the run record, requires the recorded worker pid and start token to match the live process under the run-liveness identity rule, sends SIGTERM, and waits (60 seconds by default, at most 300) for the run's project lock to be released and the record to reach a terminal state. It emits one JSON object `{runId, cancelled, lockReleased, terminalStatus}`; a dead, terminal or mismatched worker returns `cancelled: false` with reason `worker_not_live` and sends no signal, and the worker records a delivered signal as cancel source `signal_sigterm` through the existing cancellation path (cancellation carries closed `cancelSource` values `signal_sigterm`, `signal_sigint`, `internal_deadline`, or `unspecified` only on cancelled failures, while normal exit 76 remains an ordinary exit). A failed check's evidence redacts credential-shaped tokens before tail truncation (16 KiB per stdout/stderr, kept in owner-only local files under `check-evidence/<attempt>-<check position>.log`, attempt 0 is the baseline) and never returns raw evidence in JSON; the result carries only `outputPath` and, when the check's redacted output names a path the sandbox denied (a Seatbelt `deny(N)` trace or an `Operation not permitted`/`EPERM` line), that path as `sandboxDeniedPath` in the failure details. Diff rejections carry a closed `diffRejection` reason kind with up to five bounded paths. Check readiness failures name the one-based `checkIndex` and bounded executable basename under the `validate_commands` setup step. Setup refusals (`check_dependencies_unverified`) now name their `dependencyCheck` cause (including `path_dependency_changed`, and for a refused declared path dependency the rule it failed, such as `path_dependency_outside_project_parent`) and the failing `checkSetupStep`, and a failed sandboxed `npm ci` setup keeps a redacted evidence tail at `<evidenceDir>/setup-0.log`; the run record's failure details name it as `outputPath`, with a `checkEnvironmentSignature` when the output matches a known environment failure; the tail's bytes never enter an error message. Guard answers that re-report an earlier state are not logged again, and a logging failure never changes the routing answer.

Environment failures, including `deadline_expired` during routing, preparation, diff capture or integration, count as `task_failures` when this task exhausts providers in any invocation. They do not exclude providers from other tasks or latch the run to native. Failure decisions share `diagnostics/failure-semantics.mjs`; a base-derived golden table preserves existing quota-evidence, blame and disk-compatibility differences pending the owner’s decisions.

Simple dispatch also accepts `--report <path>` for read-only report tasks (mutually exclusive with `--file`, `--allow-manifest`, `--allow-executable`, `--check` and `--dirty-overlay`; the report path must not exist, is the only allowed change, and success returns `resultKind: "report"` with its bytes and sha256) and `--format <command>`, one bounded formatter run in the check sandbox after the provider and before acceptance checks (a nonzero exit is advisory and recorded as `formatStatus`; its edits are revalidated against the declared scope). Checks are dry-run against the base tree before provider start; a pre-provider environment failure stops as `check_environment_failed` and records the command identity, classified signature, and available evidence path in routing-run state. A later task in that run with the same check command stops as `check_known_broken` and returns the stored evidence before allocating another attempt; post-provider acceptance failures are not remembered. A provider that reports a rate limit is stopped at once as `quota_exhausted`, and that target stays ineligible for an hour; a provider ended at the caller deadline is coded `provider_deadline_exceeded`. After a soft failure the next target continues from the retained in-scope partial when the writer is proven stopped and the capture verified. An attempt whose checks passed but whose integration was refused because HEAD moved (`host_concurrency`) stops with that reason and its retained partial instead of rerouting, so the captain applies the partial onto the new HEAD.

Successful reports add `report.citationCheck`, bounded advisory diagnostics against the stopped, scope-validated disposable checkout: repository-relative `path:N[-M]` tokens (including Markdown link destinations) are checked against exact line ranges, and one preceding backticked identifier in the same sentence is matched as a complete token. `status` is `matched`, `issues`, or `unverifiable`; counts and up to 20 closed-reason diagnostics point to report lines without exposing source excerpts. There is no basename or nearby-line fallback. Multiple or absent identifiers, unsupported paths/forms, symlinks, sensitive paths, unreadable/binary files, and scan limits remain unverifiable. The scan caps report bytes at 256 KiB, each source at 1 MiB, total source bytes at 8 MiB, citations at 128, and each range at 100 lines; `truncated` marks an incomplete scan or omitted diagnostics. No recognizable citations is unverifiable. Matching establishes lexical presence only, never the semantic truth of a claim; citation diagnostics do not fail a report or change the existing path/bytes/sha256 fields.
To close a dangling pending attempt after unconfirmed cleanup, run `switchyard-dispatch routing-run close-pending --project <path> --routing-run-id <id> --task-id <id>`. `--task-id` takes the value given to `simple` or the persisted task hash. Recovery requires a matching terminal run record, a quiescent writer, no held project lock, and no retained worktree on disk; success marks the attempt skipped with reason `lifecycle_recovered`. A retained claim whose root and quarantine were both deleted from outside no longer blocks it (release-partial cannot reach a still-pending attempt). Salvage or discard a retained partial that still exists first with `routing-run release-partial`.
Eligible undeclared edits remain available and are returned in `undeclaredPaths` for captain review; unrelated commits may advance project HEAD during a run. Routing skips a target whose observed p80 cannot fit the remaining deadline, except when pinned with `--only-provider`; an all-slow unpinned pool is kept and flagged. After a failed or timed-out attempt, routing stops with that outcome instead of starting another target when less than two minutes, or a tenth of the task's initial budget if smaller, remain before the deadline.

**Held integration:** when another session asks the caller to hold integration of a shared file, run the task with `simple --integrate hold` instead of cancelling it. The run does everything a normal run does, including every acceptance check, the head-advance recheck and the integration gate's scope, manifest-review, structural and `git apply --check` refusals, but writes nothing to the project. The verified patch and a receipt go to `<run store>/<runId>/held-integration/` (owner-only), the run record's terminal summary has status `held` and names both files with their SHA-256 digests, and the result carries `integration: {mode: "hold", state: "held", receiptPath, patchPath, verifiedHead, ...}` with the outputs the patch will produce. The project lock is released when the run ends, as for any other run. A held run is a succeeded attempt for routing and accountability, never a provider failure, and an unapplied hold cannot serve as a `--predecessor-receipt` because its output is not in the tree. Held integration supports reports and captured dirty overlays; schema-3 receipts bind report metadata or the original overlay identity without raw overlay bytes. When the peer is done, `switchyard-dispatch routing-run apply --project <path> --run-id <runId> [--timeout <minutes>]` integrates that same patch: it takes the project lock under its own short run record, re-reads the held run, refuses a record that is not that run's own and any receipt or patch whose digest differs from the record, and re-runs the gate against the current HEAD. HEAD must descend from the verified HEAD without touching a declared path, peer history may change no manifest or executable, ordinary scoped files must be clean and unchanged, captured writable/read-only overlay inputs must still match their original identity, and when HEAD moved the acceptance checks re-run in a sandboxed checker (within `--timeout`, default 10 minutes, at most 30) that must be proven stopped and removed for the recheck to pass. A check the held run accepted by differential acceptance is rechecked against the base-tree test results its receipt stores (receipt schema 2 or 3), as the run's own head-advance recheck is, so an unrelated peer commit no longer refuses it while a peer's new failing test still does, with `differentialReason` (such as `new_failure`). The receipt keeps only a qualifying baseline whose every test id and file can be stored verbatim (no control characters or credential-shaped text, at most 1,024 characters), within 20,000 tests and 1 MiB in all (including JSON array punctuation); exceeding either total cap stores no baselines and every check rechecks strictly. Any other check, and every check of a receipt written before baselines were stored (schema 1), rechecks strictly, and stored baselines that fail validation refuse `held_receipt_invalid` with `detail: "differential_baselines_invalid"`. Before the gate may write, the held record is claimed as `applying`. It prints one JSON object; a refusal exits 1 with one closed `reason`: `held_run_not_found`, `held_receipt_invalid`, `held_receipt_consumed`, `held_receipt_stale` (with a `detail` such as `declared_path_committed`, `declared_path_dirty` or `peer_history_unsafe`), `held_recheck_failed`, `held_patch_conflict`, `held_scope_refused`, `held_apply_failed`, `held_apply_state_unknown` or `project_lock_held`. Only `held_apply_state_unknown` may have changed the tree; it keeps the `applying` claim, and every later apply refuses with `detail: "interrupted_apply"`, so the owner checks the tree (the patch stays at `patchPath`) instead of the patch being written twice. `routing-run inspect` lists each attempt's held integration under `heldIntegrations`, with its state (`held`, `applying` or `applied`) and the last apply refusal.

Applied holds may serve as predecessor evidence only when the original held run and its exact successful apply run have complete cleanup, matching receipt/patch/task bindings, and unchanged canonical HEAD/output bytes. Use the returned apply result's `runId`, `baseRevision` and `outputs`; held, interrupted, unconfirmed, forged, stale or cleanup-failed evidence refuses. Overlay rechecks reconstruct only the exact captured writable/read-only inputs and preserve the original overlay hash across unrelated HEAD advances.

`switchyard-dispatch routing-run reconcile-held --project <path> --run-id <held-run-id> [--timeout <minutes>]` retries only lost metadata after an exactly bound, clean terminal pre-mutation refusal (`held_patch_conflict` or `held_scope_refused`). Under the project lock it requires worker quiescence, affirmative checker cleanup, original verified HEAD, full clean scope and unchanged inputs. The audited transition returns the receipt to held without replaying or undoing project bytes. Unknown/consumed mutation, drift and missing proof—including historical applying claims without exact apply binding—remain refused. A dead parent or restored inputs alone is insufficient.

**Provider launch evidence:** primary and correction runs persist at most two bound `providerLaunches` entries, beginning as `starting` before spawn. Available early PID/group/start observations are persisted during invocation; missing identity remains `identity_unavailable`, and a `ps` start stamp is explicitly seconds-precision. Required publication precedes stdin delivery; argv-based prompts are already visible at spawn and may start upstream work before publication. A publication failure stops the supervised writer and waits for teardown, without attributing a host write failure to the provider. An OS spawn can precede durable observation if the parent crashes. These records supply provenance, not signalling/recovery authority or proof that escaped descendants stopped; the legacy missing-identity run remains contained.


Simple acceptance checks use fresh, provider-unexposed checkers beneath the task's durably owned root. Checker Git clones dissociate from the project object store before entering Seatbelt, so sandboxed Git commands do not need access to host object paths; a matching inaccessible-alternate error in the pre-provider dry run is classified as an environment failure and stops before provider launch. Checks that fail plainly on the unmodified tree are recorded as `redAtBaseline` and named in the provider prompt and in the repair prompt. Such a check that runs `pytest`, `python -m pytest` or `node --test` as a plain argv with only allowlisted flags is judged differentially: the dry run captures its per-test results through a machine-readable reporter (pytest junit `xunit1` with `--maxfail=0`, or a node JSON-lines reporter), and a later failing run is accepted only when the runner exited 1 on its own, its report is complete, no test timed out or was killed, no test fails that did not fail at baseline, no baseline test is missing or newly skipped, the test count did not drop, and the task's targeted tests (new ones, or any in a declared file) all pass with at least one passing. The check result carries a `differential` record with the verdict, its reason, and the baseline and after failure sets, bounded to 20 redacted ids each. When every check passed, the result's top level says how: `checkAcceptance` is `differential` if any check passed under this rule and `strict` otherwise, and `toleratedBaselineFailures` counts the pre-existing failures those accepted runs still had; `run.json`'s `terminalSummary` and a failed attempt's failure-log record carry the same two fields. The recheck after HEAD advanced judges against the original base tree's baseline, and its verdict is the one the result reports. The provider prompt and the repair prompt tell the provider which red checks are judged test by test (its own tests must pass and no new failure may appear) and keep the earlier wording for the rest. Every other check, including `swift test` and a check whose baseline report could not be captured, must still exit 0. A plain command that runs a declared `--file` script absent from the base tree (`bash tests/new-test.sh`, `./tests/new-test.sh`, `node`/`python3` on a relative path) and fails `tool_missing` is recorded the same way instead of stopping; the same failure for an undeclared script, or a declared script that exists in the base tree, still stops. A disposable preflight checker replays the exact saved base and dirty overlay, probes Seatbelt, resolves requested tools, and runs configured baseline checks; its removal is confirmed before provider launch. After stopped-writer proof, every initial or repair candidate gets a new checker with the scope-gated diff. The supported checker backend is macOS on Apple Silicon, with Node and npm installed under `/opt/homebrew`. Node/package-tool checks that need dependencies require the entire unchanged locked tree, fixed offline `npm ci --ignore-scripts`, and a warm trusted npm cache mounted read-only. Missing cache entries, unsupported configuration, unavailable confinement, or changed manifests for Node/package-tool checks fail closed; no network or host `node_modules` reuse occurs. Generic scope checks do not require a Node dependency cache; an owner-approved exact interpreter/base tree and declared read-only dependencies (granted inside the project's parent; a linked git worktree that its main checkout lists uses the main checkout's parent, and an unverified one gets no grant outside its own checkout), along with swift build/xcodebuild build caches in the clone, are supported, while simulators/tests/signing/keychain and broad tool prefixes remain denied. Checks have a minimal environment, live progress, cancellation, and the original deadline. This is accident containment: a detached descendant that leaves both the process group and clone directory is not proven stopped.

Results with executed acceptance checks include `checkLimitations`: passing checks, including package builds, do not establish that app targets were compiled. The same disclosure is persisted in `terminalSummary`; app-target compilation requires a native app-target build.
Check commands are rejected before execution when they use shell expansion, denied host tools, or absolute paths outside the clone. Checkers receive a fixed `PATH`; a local `xcrun` shim answers SDK queries from `DEVELOPER_DIR` and delegates tool invocations through that path, with `SDKROOT` set when available to avoid host Xcode-selection and license probes. Dependencies are limited to the unchanged locked Node install, declared read-only paths, and clone-local build caches; Swift package checks must use `swift build --build-system native --disable-sandbox`. Simulator, test, signing, and keychain tools remain denied.

Before launch admission, every simple attempt checks that the CLI its lane execs still honors the lane's flags (`--version` parses, `--help` lists each flag the argv builder passes), offline and without credentials; a drifted or missing CLI fails as `provider_cli_contract_failed` before any provider start and routing moves to the next target. `npm run cli:canary` reports every adapter (`--json`, `--only codex,vibe`). Vibe, Vibe Code, and OpenCode launch admission probes sandbox availability before provider start. An unavailable launcher environment returns `launcher_environment_unavailable` with no provider invocation; the dispatcher does not elevate automatically. Failed runs persist their terminal failure and pending cleanup intent before destructive cleanup, then persist the final disposition even when no clone was allocated. Failed persistence cannot certify completed cleanup.

Unrecognized failed-provider exits retain only a redacted 4 KiB stderr tail in an owner-only artifact beneath the validated run directory; terminal JSON and run records carry only its path. Broad-permission or symlinked storage is refused without replacing the primary failure.

Provider reliability diagnostics use a closed version-1 record: cause category/code and phase, bounded process/check evidence, baseline status, diff-rejection category/count, and one-repair status/count. They omit provider output and prompt content. Simple dispatch opts into pre-provider checks with repeatable `--baseline-check`; these remain separate from acceptance checks and fail closed on uncertainty or detected mutation. Checks whose results depend on the absolute checkout path (for example `swiftlint --baseline`) must be passed as `--baseline-check` so pre-existing findings are known before the provider runs. Simple dispatch runs one scoped correction after a failing acceptance check within the original deadline by default; `--no-repair-checks` disables it and `--repair-checks` remains accepted for compatibility. A repair is its own provider invocation and keeps its own route-health invocation identity. Pre-provider baseline checks are opt-in; acceptance-check repair is on by default. These features do not change roster data or provider eligibility. Simple dispatch enforces route health by default and opts out with `SWITCHYARD_ROUTE_HEALTH_MODE=shadow`. Health can only suppress an otherwise eligible route.

`node scripts/provider-qualification.mjs` provides an offline inventory of active configured target descriptors; `--target ID --capability low|standard|high` plans one exact descriptor. Inventory and planning do not call providers or promote descriptors. Representative execution is a separate explicit `--execute --deadline RFC3339` operation, and its result never promotes automatically.

**Status:** `simple` is the only dispatch path. `switchyard-dispatch` runs `simple`, `routing-run`, `recover`, `health`, `doctor` and `remediate-orphaned-locks`, plus `--version` and `--help`. Any other subcommand, including the retired `run`, `launch`, `validate-inputs`, `backend-health`, `status` and `result`, exits 2 as unknown.

**Target contract:** a roster target's ID, `billing_provider`, `usage_provider`, funding policy, slots, and priority own accounting and admission; its `harness` selects the execution adapter. The selected `vibe` target uses `harness: "vibe"`: low routes `glm-5-3-medium` with medium thinking, while standard routes `glm-5-3` with max thinking. The simple keyless bridge writes a task-local Vibe configuration, verifies Vibe's recorded active model, and does not inherit OpenCode credentials or identity. Harness, selector, and invocation details participate in descriptor identity, so each exact descriptor needs its own receipt.

**`vibe-code` target (simple lane only):** Mistral bills the API allowance and the Vibe Code allowance by credential, not by request shape. `vibe` spends the API allowance through the BWS key and the keyless bridge. `vibe-code` runs native headless `vibe -p` on Vibe's own keychain login (service `ai.mistral.vibe`) through `ops/simple-vibe-code-launcher.mjs`, so it spends the Vibe Code allowance. The launcher scrubs `MISTRAL_API_KEY` (Vibe resolves the environment variable before the keychain), runs Vibe under `sandbox-exec` with a fake `HOME` that links only the login keychains, enables only the `edit`, `write_file`, `read_file` and `grep` tools, and verifies the session's active model alias. Each target needs its own usage-snapshot entry (`Vibe` and `Vibe Code`) so one empty allowance does not veto the other.

**Admission:** automatic admission is descriptor-bound. Read the current eligibility from `npm run roster:coherence` rather than from a dated list in this file.

## Priorities (in order)

1. **Containment & isolation (security).** The sandbox boundary *is* the product. A misbehaving provider process must never reach the owner's checkout, host credentials, or another provider's environment.
2. **Correctness of the integration boundary.** A declared-file allowlist, structural diff validation, and reviewed apply through the integration gate, with a complete provenance record for every task. The host never applies un-reviewed provider output.
3. **Provable containment.** The boundary is *proven*, not assumed: the INV-1 gate (the `tests/simple-dispatch-*` suites named in `INVARIANTS.md`) exercises the disposable-clone and provider-sandbox contracts. This is containment against a misbehaving agent, verified, not a claim to withstand a targeted attacker.
4. **Observability & auditability.** Every task records which repository snapshot, routed target, patch, and validation result belonged to it.

## Workflows

### Host diagnosis (`doctor`)

```bash
switchyard-dispatch doctor          # every check, with fixes
switchyard-dispatch doctor --quick  # state-file checks only
switchyard-dispatch doctor --json   # {schemaVersion: 1, status, checks}
```

`doctor` is read-only: beyond the CLI canary's `--version` and `--help`, it never runs a provider CLI, and it never takes a lock or reads a secret. Each check prints one line, then any indented detail lines, then one indented `fix:` line per action:

1. `sandbox-toolchain`: `node`, `npm` and `uv` resolve inside the real check sandbox profile.
2. `provider-clis`: the launch-admission CLI canary (`npm run cli:canary`), with one detail line per adapter. A CLI that dropped a flag its lane passes, or a canary run that was inconclusive (a step timed out, or the 120 s budget ran out), warns; a CLI that is missing or cannot answer `--version` or `--help` fails. Each fix line is the canary's remedy, or the `cli:canary` rerun for an inconclusive CLI. The canary does not compare versions with `ops/macos-vm/cli-manifest.txt`; `sync-host-clis.sh --check` does.
3. `bridge-pins`: each `switchyard-*` broker consumer's executable SHA-256 against its pin in the bws broker registry (read as text).
4. `qualification-expiry`: active roster slots whose newest `dispatch_qualified` receipt has expired or expires within 9 days.
5. `repair-holds`: route-health repair holds, each with its `health attest-repair` command. Commands use the current simple configuration epoch. Holds for inactive descriptors remain visible without a repair command; attestations for an older configuration are not reported as awaiting a current trial.
6. `stranded-pending`: stranded pending routing attempts, with `routing-run close-pending` when it would accept them, else `routing-run inspect`.
7. `launch-agents`: the sandbox canary LaunchAgent and its freshness. It also warns while the retired reaper LaunchAgent is still installed, and prints the `launchctl bootout` and `rm` fix that removes it.

`FAIL` means a probe failed or a pinned identity is broken; `WARN` means a route is or soon will be unavailable until the owner acts. Exit status: 0 when nothing failed (warnings allowed), 1 when a check failed, 2 on a usage error. `simple` runs the quick subset at start and prints one stderr line only when a check finds a problem. Qualification and holds are small synchronous file reads; the pending scan runs only for a caller-supplied routing run ID and is cut off after 2 seconds.

#### Git hooks

Git runs two tracked hooks from `.githooks/` in every checkout and linked worktree once `npm install` has run the `prepare` script (`git config core.hooksPath .githooks`). `core.hooksPath` is repository-wide, so a worktree needs no setup of its own, but it needs `node_modules`: a worktree without them fails the commit in the hook instead of skipping the gate.

| Hook | Runs | Why here |
| --- | --- | --- |
| `pre-commit` | `npm run lint`, `npm run deadcode`, then the staged file-size and contract-receipt checks | Fast enough to sit in front of every commit. |
| `pre-push` | `npm run validate:host` | Lint, deadcode, the full suite, roster coherence, the host sandbox canary, and six executed Python host cases — the heavy gate, once per push. |

The hooks invoke the named scripts rather than restating their steps, so they cannot drift from the gate. That drift is the failure they exist to stop: `knip` went red at `a4138a5` and three commits landed on top of it before anyone ran `validate` by hand.

Pre-push writes `.logs/pre-push-<short-sha>.log`, preserves the host gate exit status, and prints the first failing test lines, host load and log path on failure. The gate receives closed stdin and clears repository-local Git variables before its fixtures run.

**These hooks are the whole enforcement story — there is no CI, by decision (2026-08-14), not by omission.** This is a solo repo, and the strict gate (`validate:host`) needs this Mac's Seatbelt and Homebrew toolchain. The accepted cost: hooks are bypassable with `--no-verify`, and a fresh clone has none until `npm install` runs `prepare`. Run `npm install` before your first commit.

When checking a gate from a script or a terminal, do not pipe it: `npm run validate 2>&1 | tail -60` reports **tail's** exit status, not the gate's. That is what hid the red build. Redirect to a file and check `$?`, or read `$pipestatus[1]` in zsh (`${PIPESTATUS[0]}` is the bash spelling and expands to nothing under zsh).

#### Host sandbox canary

Ordinary `npm run validate` runs inside confinement, where Seatbelt cannot nest, so its checks stay portable. The strict host gate is `npm run validate:host` (`scripts/run-host-validation.mjs`), which runs ordinary validation, requires six executed Python host cases with no skips, and runs the explicit host sandbox canary (`scripts/sandbox-canary.mjs`, `npm run canary:sandbox`). The canary runs real probes through the installed check profile: `sandbox-exec` availability, a basic process, module self-host, confinement write-denial, safe-env inspection, and the toolchain sandbox suite. Toolchain probes share the remaining 300-second overall canary deadline. Availability diagnostics distinguish timeouts, signals, spawn errors and sandbox denial; notification failures name the notification tool. These diagnostics do not establish the cause of earlier failures.

```bash

node scripts/sandbox-canary-daily.mjs   # UTC-day dedupe + transition notification
```

### Simple Local Dispatch

Use this for an ordinary bounded implementation. The prompt is a regular local file; every permitted output file and local verification command is explicit.

```bash
deadline=$(date -u -v+15M +%Y-%m-%dT%H:%M:%SZ)
/Users/dave/.agent/bin/switchyard-dispatch simple /absolute/task-prompt.md \
  --project /absolute/project \
  --capability standard \
  --file src/example.mjs \
  --file tests/example.test.mjs \
  --check 'node --test tests/example.test.mjs' \
  --deadline "$deadline"
```

`--deadline` may be at most 30 minutes ahead (`--timeout` takes 1 to 30 minutes). Tasks in one project run one at a time: the project lock is keyed by the canonical project path, not the routing run, so a second `simple` in that project fails at once with `PROJECT_LOCK_HELD`, even under a different `--routing-run-id`. `--check` commands run through `/bin/sh -lc`, so shell syntax such as `&&` and pipes works; a check that launches a package tool (`npx`, `npm exec --`, `node_modules/.bin/<tool>`, a lockfile-declared bin, or any `npm`/`pnpm`/`yarn`/`bun` command) instead runs as plain argv with no shell from the locked local install, accepts only letters, digits and `. _ / @ : + = -`, and is otherwise refused as `check_dependencies_unverified`. `simple --help` states the same.

Progress goes to stderr and stdout contains one bounded JSON result. After the terminal milestone, a finalization step (durable writes, project-lock release, check-session and worktree cleanup, failure disposition) that keeps waiting is reported every minute as `dispatch: simple finalization step=<name> waiting_ms=<n>`, plus `fs_probe_pending_ms=<n>` when a filesystem probe has not returned (a sign the libuv threadpool is stuck). A step that blocked the event loop for 10 seconds or more is reported as `event_loop_blocked_ms=<n>` once the loop resumes. These lines report only; they never time out a step. Use either `--deadline <RFC3339>` or `--timeout <minutes>` (1–30) as a relative deadline alternative. RFC3339 deadlines require uppercase RFC3339 with an explicit Z or numeric offset; fractional seconds may contain one or more digits and are truncated to milliseconds, while discarded nonzero precision still counts against the 30-minute maximum. That limit covers execution, checks, integration, and cleanup. A provider gets one attempt; failures name the phase and preserve a useful disposable checkout when possible. The clone shares object reads for speed but has independent Git control data, so provider Git operations cannot alter the owner repository's branches, index, or linked-worktree records. The host project is locked, pre-existing or concurrent edits to declared files are refused, undeclared changes are rejected, and provider output, prompts, commands, environment, and credential values are absent from the receipt. The local adapters are target-aware: Codex is launched ephemerally with `workspace-write` and ignored user configuration; `antigravity` launches Agy with the routed Gemini selector; `antigravity-claude` launches the same harness with its separate Claude selector; and `copilot-student` launches Copilot with its session sandbox and an edit-only tool allowlist. Every process starts with the disposable checkout as its working directory, and target, harness, and exact selector must agree before routing and again before invocation. When a caller already runs inside an OS sandbox, the installed Switchyard launcher must be authorized outside that parent boundary so Copilot can create its own nested session sandbox. (The tier-1 Codex Spark target that also served eligible low work here was retired by the owner on 2026-09-19.) Vibe low and standard use a content-pinned BWS consumer and keyless Seatbelt bridge in the disposable clone; both passed exact one-file simple canaries on 2026-09-25. The bridge passes `--auto-approve` to programmatic Vibe so its non-edit tool calls are not denied by the CLI's unattended approval handler; the unchanged Seatbelt profile still confines file writes and network access. A succeeded run then renews its receipt through the roster CLI (`src/switchyard/simple/receipt-renewal.mjs`), after the JSON result is written; progress and any skip reason go to stderr.

A run store write fault fails closed before provider launch, and terminal persistence failure cannot publish success. **Caller disposition:** the lock-conflict receipt carries a bounded, closed `disposition` object projected by `dispatch/disposition.mjs`:

```json
{"disposition":{"version":1,"action":"monitor|defer|policy_deferred|recover|repair_contract|target_failed|complete|stop","direction":"repair_input|advance_authorized_fallback|recover_and_retry|retry_launch|wait|complete|stop","reasonCode":"closed_code","diagnosticCode":null,"taskId":null,"blockingRunId":null,"recoveryCommand":null,"failedTargetIds":[],"failedTargetIdsTruncated":false}}
```

`direction` is a pure total function of `(action, reasonCode, diagnosticCode)` in `baseDisposition`; an unenumerated tuple returns `stop`. It is run-local evidence only and never authorizes, selects or invokes a route.

| Closed direction | Exact mapping |
|---|---|
| `repair_input` | Contract repair, or a target failure classified as required/undeclared/no-op/seed/manifest/patch/conflict input evidence. |
| `advance_authorized_fallback` | A target failure classified as provider execution, exhaustion, cleanup, diff-capture failure, or an empty provider result, or a battery-policy deferral carrying the exact next task ID. | `recover_and_retry` | `recover` with a state-root-bound recovery command; after recovery the caller re-enters normal preflight. |
| `retry_launch` | A terminal lock diagnostic without fresh holder classification; rerun normal preflight without acting on a stored holder identity. |
| `wait` | `monitor`, or a holder-aware pre-initialization `defer`. |
| `complete` | Terminal `complete`. |
| `stop` | Authentication, containment refusal, recovery/cleanup failure, insufficient evidence, or any unknown tuple. |

Every supported Python manifest (`pyproject.toml`, `uv.lock`, `requirements.txt`, `setup.py`, `setup.cfg`) present on either side must be regular and byte-identical, a candidate-provided `.venv` entry is refused, and the runner imports candidate code without inheriting `PYTHONPATH` while redirecting Python/pytest caches into the runtime. Real pytest execution and confinement proof belong to the serial host suite, which requires an existing installed-pytest venv through `SWITCHYARD_TEST_PYTEST_VENV`; unset, it checks the checkout-local `.venv`, then the parent directory `.venv` (also used by composite phase fixtures); the suite never installs dependencies. An unconfigured missing fixture is skipped as unavailable by the portable suite and is never execution proof; the strict host gate independently refuses that result. An explicitly configured unusable fixture fails visibly.

**Local check host tools:** for local checks, the additional host tool trees are fixed to /opt/homebrew/bin, /opt/homebrew/Cellar, the trusted user's ~/.cargo/bin, and ~/.rustup/toolchains; Homebrew's existing /opt/homebrew/opt read remains. The checker also reads the exact /private/etc/ssl/openssl.cnf literal for system TLS initialization. Other host home files, including Cargo configuration or credentials and Rustup settings, stay unreadable from inside the checker; other processes' argv and environment are the exception described in the threat model above. Before a check, Switchyard selects the host's configured default installed toolchain through a bounded, sanitized rustup show query with automatic installation disabled. Per-project toolchain overrides and explicit +toolchain selectors are unsupported. Cargo's home, target directory, and caches live inside the disposable check runtime, and Cargo is forced offline; every other additional host input remains denied.

**OpenCode Go runtime:** The simple bridge runs Homebrew's OpenCode 2.x at `/opt/homebrew/bin/opencode`, so Homebrew upgrades apply without a bridge change; the CLI contract canary checks its `run` and `serve` flags before each attempt. OpenCode 2.x has no in-process run mode, so the bridge starts `opencode serve` on a free loopback port and then `opencode run --server` against it. Both run under one Seatbelt profile that adds bind, inbound and outbound rules for that single port to the proxy-only rule. The server demands a random per-run `OPENCODE_PASSWORD`, and the client, which carries it, starts only after this server child prints its own listening line; both process groups stop on every exit path. The ephemeral config sets the proxy endpoint on the approved `deepseek-v4.1-flash` catalog model itself, because a V2 catalog model's own endpoint outranks the provider's, and pins low/max to `reasoningEffort`. A fixed `--title` skips the separate title-generation request. Project config, Claude Code imports, the models fetch and the file watcher are disabled.

A bridge failure prints one fixed `simple-provider-keyless-bridge:` reason with trusted status tokens and never provider text, and exits 76. When that reason is the last stderr line and reports a signal or an interrupt, the runner records `providerSignature: provider_killed` (or `provider_deadline_exceeded` when the bridge's duration limit or the runner's own deadline drove the kill); returned child lines that start with a reserved bridge prefix (`SWITCHYARD_`, `simple-provider-keyless-bridge:`, `switchyard:`) are framed `child: `, and forwarded output also redacts every 12-character window of the key. Any change to the bridge bytes breaks both the Vibe and OpenCode Go lanes until the owner re-pins both BWS consumers. The native Claude Code and Vibe Code launchers end the same way: a provider stopped by a signal or by the launcher's duration limit, `SIGTERM` or `SIGINT` prints `simple-<name>-launcher: failed closed (simple-<name>-launcher: provider terminated before a verified completion (code, signal, error, interrupt))` and exits 76, which the runner types the same way, and returned child stderr lines that start with `simple-<name>-launcher:` are framed `child: `.

**Provider request log:** the Vibe and OpenCode Go simple bridge has no fixed chat-request limit. The simple run deadline still bounds execution. Every proxy request emits a closed, content-free outcome record; the host saves these records as `provider-requests.jsonl` (`provider-requests-repair.jsonl` for a repair attempt) in that run's `.logs/switchyard/runs/<runId>/` directory. Each line identifies request sequence, elapsed time, duration, proxy HTTP status, upstream HTTP status, and a fixed outcome category. A final `end` record certifies the number of requests allocated; an absent or mismatched marker makes the run fail closed. The log never contains prompts, headers, URLs, bodies, nonces, credentials, or raw provider output. BWS consumer pins and verification results are recorded in `HISTORY.md`.

**Simple root retention:** A terminal run removes its disposable root after the result is durable unless it is explicitly retained for salvage or cleanup is uncertain. Writer teardown settles its process group and checks for newly launched processes still holding the exact clone cwd; an unprovable process state retains the root. Roots live in an owner-only `$TMPDIR/switchyard-simple-roots/` parent (mode 0700, never a symlink) rather than directly in the shared temp directory, so a sweep or glob of `$TMPDIR` children no longer reaches live checkouts; a delete of the whole temp directory still can, and the run then reports `worktree_missing` instead of blaming the provider. A failed run never advertises a retained checkout that is gone when its terminal record is written: `partialWorktree` is null, `partialWorktreeLoss` is `worktree_missing`, and the run record shows the worktree `removed` with that reason. `node scripts/sweep-temp-dirs.mjs --simple-orphans` inventories current UUID-named simple roots in that parent and, for older runs, directly in the temp directory, with a 24-hour whole-tree TTL, owner marker, run-record, and complete open-handle checks. It is dry-run by default; `--apply` reclaims old, dead retained salvage roots only when the recorded nonce, device, inode, marker, full-tree age, and open-handle evidence all agree. Symlinks inside a tree are measured without following them. Markerless roots remain protected from automated deletion. Legacy six-character roots are inventory-only; the 2026-09-27 backlog was moved to Trash after separate age, ownership, run-store, and open-handle checks.

**Exact allowlist enforcement:** Simple dispatch passes the declared output scope directly as `allowedPaths` to the integration gate. Changing any subset of declared outputs succeeds; any undeclared addition, modification, deletion, or rename endpoint fails closed with `undeclared_paths_changed`. Ambiguous combined rename spellings (containing `=>`, `{`, or `}`) are rejected. A move is captured as a delete plus a create, so both endpoints must be declared.

**Manifest opt-in:** Declared manifests matching the integration gate's build/execution patterns, including `*.sh`, are refused by default before any provider starts. `--allow-manifest <path>` admits one path that is also a `--file`. A declared manifest omitted from `--allow-manifest` still fails at input validation with `manifest_review_required`; the result's `hint` and one stderr line per refused attempt name the exact `--allow-manifest=<path>` flag (shell-quoted when needed) for each of up to five printable manifests and count the rest. An edit to an undeclared or `--input` manifest fails at diff validation with `undeclared_paths_changed` or `read_only_input_changed`.

**Executable opt-in:** Any diff that sets an executable bit is refused with `executable_file_refused` by default. `--allow-executable <path>` admits one path that is also a `--file`, once per path, and is mutually exclusive with `--report`. For that exact path the diff may only create a regular 100755 file or change an existing file from 100644 to 100755. A symlink turned into an executable, deleting an executable, and an executable bit on every other path still fail with `executable_file_refused`; a diff in which any touched name is not valid UTF-8 or contains a newline receives no executable grant at all; symlink creation still fails with `symlink_creation_refused`; and an existing symlink at the path is refused at argument parsing, even under `--dirty-overlay`. Renames and copies cannot carry a bit past this rule: simple captures provider diffs and peer history with `--no-renames`, so a move is a delete plus a create that states both modes, and `validateDiff` refuses any rename or copy line it still receives with `executable_file_refused`, because a pure rename patch states no mode. Moving a plain declared file still integrates; moving an executable fails even with the opt-in, since its deletion is never granted; copying an executable, or moving a file and setting its bit, needs the opt-in on the destination; and a peer commit that renames or copies an executable stops the run as `host_concurrency`. The opt-in is independent of `--allow-manifest`, so a new `*.sh` script needs `--file`, `--allow-manifest` and `--allow-executable`. It reaches the provider diff checks, the check session's candidate gate and the final integration gate, but never undeclared edits kept for review, peer history after a HEAD advance, or a partial-continuation carry. When used, it is recorded in the routing task identity scope; an unused opt-in leaves existing identity hashes unchanged.

**Versioned predecessor continuation:** For an explicitly authorized task-scoped dirty baseline, add `--dirty-overlay`. Every writable path remains a repeated `--file`; every necessary read-only path is a repeated `--input` and is copied into the disposable checkout but rejected if the provider changes it. This mode supports tracked dirty inputs as well as bounded regular untracked prerequisite transport when explicitly declared and proven by an accepted predecessor simple-attempt durable receipt via `--predecessor-receipt <path>`. A successful simple result includes its base revision and output digests; the consumer resolves its run ID back through the run store and requires a succeeded result for the same canonical project with matching durable output evidence. Dirty overlay receipts are versioned (schema version 2); predecessor transport binds run identity, base revision, relative path, byte size, and digest. Missing, fabricated, cross-project, or mismatched predecessor evidence, symlinks, special files, ignored files, secret-shaped paths, or byte drift fail closed before provider execution or integration as applicable. Dependent tasks run in a fresh disposable clone with no host commit.

`providerLifecycle` is an additive, bounded diagnostic receipt. It preserves schema version, PID, supervisor start/deadline/last-output timestamps, observed silence, terminal status and reason, exit/signal, writer state, and cleanup outcome without output, prompt, argv, environment, or error text. Silence is observational only: buffered or quiet work continues until the existing absolute deadline or cancellation contract decides termination. Empty completion, spawn/admission failure, deadline expiry, cancellation, and uncertain cleanup remain distinct outcomes. The low-level simple engine does not retry a failed provider; the command-facing routing-run wrapper may continue to another eligible tier 1 or tier 2 target, excludes provider-accountable failed targets for the rest of that run and any soft-failed target for the rest of that task. A caller SIGTERM/SIGINT cancellation or a live quota exhaustion does not exclude the target from later attempts at the same task, a quota exhaustion also does not exclude the target from later tasks in the run once its route cooldown ends, and a quota-only exhaustion reports `capacity` rather than `task_failures`. Red baseline checks stop with `baseline_failed`, check-setup failures stop with `check_setup_failed`, hard failures stop with `unsafe_failure`, and soft failures continue to the next eligible target for ordinary tasks up to four failed attempts; pinned or high-capability tasks stop on the first soft failure, while answers report `exhaustionCause` and `retainedPartials`.

The first attended real-provider acceptance passed on 2026-09-14 through `codex-spark`. On 2026-09-21, fresh simple-path canaries passed through Antigravity Gemini low and Copilot Student low: each changed one declared fixture, passed its named syntax check, integrated once, stopped its writer, removed its disposable checkout, and released the project lock. When `simple` is itself launched from an outer workspace sandbox, that outer caller must authorize access to provider host state and subscription authentication; the selected provider still runs inside its own local sandbox rooted at the disposable checkout.

### Recovery

`recover` is the backstop for anything a hard kill (`SIGKILL`, host reboot) leaves behind. It releases only a lock it can prove is unowned by a live, still-active run, so recovering a stale run never takes a lock from a run that is genuinely in progress.

```bash
switchyard-dispatch recover [--run <run-id>] [--state-root <path>]
```

Without `--run`, `recover` releases stale and orphaned project locks. With `--run <run-id>`, it releases that run's stale lock and handles a terminal simple run's retained worktree. `--state-root <path>` selects the durable state root to reconcile. It prints one JSON envelope with `disposition` (`reclaimed`, `preserved`, `no_candidates` or `partial_failure`), `worktreesReclaimed`, `errors`, `projectLocksReleased`, `runId` and `candidates`. Simple candidates carry `runLiveness` (worker PID state, not writer proof), and a running simple target skips global project-lock cleanup to protect possible child writers.

`acquireProjectLock` writes `projectPath` into a project lock's body. Recovery first reconciles recovery claims, then scans every on-disk project lock under the selected state root, while the candidate-run pass remains as a complementary path. Both use the shared `terminal_clean`/`live`/`startup_grace`/`dead`/`unknown` classifier and ownership-checked release; only a parseable lock with a resolvable `projectPath` and an eligible terminal or dead run is auto-reclaimed. Claims are atomically renamed before deletion, revalidated, and never overwrite a replacement lock. A pre-`projectPath` claim may recover its project only from a matching run record plus the exact canonical or cwd-derived filename hash. PID-bearing recovery proofs remain protected unless their owner is proven dead. Unparseable, unresolvable missing-`projectPath`, missing-run, live, startup-grace, unknown, and cleanup-failed records remain for human confirmation.

Locks that automatic recovery must retain go through `remediate-orphaned-locks`, which keeps a human in the loop:

```bash
switchyard-dispatch remediate-orphaned-locks --dry-run --state-root <path>   # inspect the candidate set first
switchyard-dispatch remediate-orphaned-locks --state-root <path>             # asks before removing
```

It resolves candidates fresh from disk on every run, recovers `projectPath` for pre-`projectPath` locks and claims from the run's own record, confirms the exact filename hash against the file on disk, and still enforces ownership-checked release at deletion time. Without `--confirm` it asks once before removing; cleanup-failed locks and claims and missing-run candidates require the interactive prompt even with `--confirm`. It rechecks worker liveness and project identity immediately before mutation, and it never auto-removes cleanup-failed evidence.

### Route health

`router/health.mjs` keeps a host-owned, fenced projection of how each routing target has been behaving, and `simple` consults it in one of two modes. `enforce` (the default) removes held targets from the candidate set with reason `route_health_suppressed` and is the only mode that claims and starts half-open trials. `SWITCHYARD_ROUTE_HEALTH_MODE=shadow` computes and records the decision it would have made and changes nothing else: it never suppresses a target and never writes a half-open claim. Only the exact value `shadow` opts out. When health empties an otherwise eligible pool, the run fails `route_health_blocked`. That holds at the 64-entry route evidence bound too: the refusal lists and the evidence the pass takes from the router's result drop other entries before a `route_health_suppressed` entry. The router's own evidence capture still keeps its first 64 exclusions.

State lives under `<run-store state root>/route-health`, which is `<switchyard checkout>/.logs/switchyard/route-health` unless `SWITCHYARD_RUN_STORE_ROOT` relocates the run store or `SWITCHYARD_ROUTE_HEALTH_STATE_ROOT` names another root. `health inspect` and `health attest-repair` take `--health-state-root <path>` and otherwise use the checkout default `.logs/switchyard/route-health`, whatever the run-store root is. Each target's evidence is a bounded ledger (at most 512 attempts, at most 256 KiB; attempts before a target's latest success are compacted away once the ledger passes 256) plus a control record, versioned by the adapter contract `switchyard-route-health-v1`. Unreadable or malformed state yields `health-unavailable`; a suppression requires an available projection, so an unavailable one never excludes a target in either mode.

A target's state is `healthy`, `suspect`, `cooldown`, `repair-hold`, or `half-open`. Only the closed hold codes `auth_expired`, `model_unavailable`, and `cli_usage_error` create a repair hold; the transient set that drives the 5/15/60-minute cooldown ladder is `provider_exit_nonzero`, `provider_deadline_exceeded` and `provider_signalled`. A hold records the public configuration epoch (derived from the qualified-provider allowlist and a configuration reference) and the target's repair epoch it was taken under, but it is not invalidated by a configuration change: only the observation window is epoch-keyed. `simple` uses the fixed configuration reference `switchyard-simple-direct-v1`. A hold clears when a success is ingested for that target.

**Failure counting.** A provider failure counts toward suppression only when the failure registry marks it provider-caused (`providerCaused`, not the persisted `causeCategory`, which stays `unknown` for `provider_exit_nonzero`), its phase is `provider`, and Switchyard's own process supervisor corroborates it: the writer group is stopped, the lifecycle receipt is closed, and its exit status, signal or deadline termination agrees with the diagnostic (`lifecycleBackedProviderFailure` in `simple/failure-accountability.mjs`). No adapter diagnostic is needed, so an agy exit-3 crash counts. Check, scope, sandbox, environment, cancellation, cleanup and silence outcomes never count: the controller settles the provider's terminal evidence before checks, diff and scope run, and anything without a matching closed receipt is ignored. Two distinct failed attempts inside six hours put the target in `cooldown` (5 minutes); each failed re-probe advances the ladder to 15 and then 60 minutes. A simple-direct success is transport plus a closed lifecycle receipt; it carries no served-model proof (`servedModelVerified` is not set), clears earlier failures and resets the ladder. When a cooldown expires the next dispatch takes the target's single half-open claim: a successful trial clears the target, a failed one re-suppresses it with the next cooldown step, and an inconclusive trial (cancelled or otherwise not provider-attributable, with the provider proven stopped) releases the claim without counting. A trial whose provider group cannot be proven stopped stays `half-open`, as does the claim of a dispatcher that dies mid-trial, until Switchyard reclaims it: once the claim's run is terminal and cleaned up in the run store, or once the claim is 2 hours old (26 hours while the run's worker is still alive). Failures inside an active cooldown never step the ladder; only a failed re-probe does.

Leaving a hold is a half-open trial. `switchyard-dispatch health attest-repair --target <id> --descriptor <descriptor-identity> --public-configuration-epoch <epoch> --repair-kind <auth_repaired|configuration_repaired>` records a host-side attestation; a trial is available only when an attestation is newer than the newest hold at the current repair epoch. One half-open claim per target is keyed by run id, task id, and attempt. `health identity --target <id> --capability <low|standard|high>` prints the descriptor identity and public configuration epoch the other two subcommands require, and `health inspect --target <id> --descriptor <descriptor-identity> --public-configuration-epoch <epoch> --repair-epoch <n>` prints the projection; both are read-only. `health identity` derives its epoch from `SWITCHYARD_PARALLELS_GOLDEN_IMAGE` (default `golden-image-unconfigured`) rather than from the `simple` reference above, so the two epochs differ unless that variable is set to `switchyard-simple-direct-v1`.

The simple router's `origin` is supplied by a trusted local caller. `work` is the default for ordinary tasks; `qualification` marks a local qualification canary. This label is not caller authentication or a security boundary. A qualification canary skips only work route-health suppression: it still requires ordinary provider eligibility and capacity, exact descriptor qualification, and the same sandbox, scope and lifecycle checks. It adds no provider credential or alternate authentication path.

### Environment Variables

- `SWITCHYARD_ROSTER_PATH`: Optional override for the provider/harness capability roster file (`roster.json`). When unset (or empty), the loader resolves the canonical default `~/.agent/roster.json` via `os.homedir()`. Fail-loud loading is preserved: a missing or malformed roster at the resolved path (override or default) throws on load — there is never a silent fallback to an empty or wrong roster.
- `SWITCHYARD_RUN_STORE_ROOT`: Override for the run-store directory (`runs/` and `locks/` live under it; default `<switchyard checkout>/.logs/switchyard`). Primarily a test-isolation override; `recover` and `remediate-orphaned-locks` set it from their `--state-root` option.
- `SWITCHYARD_ROUTE_HEALTH_MODE`: `shadow` or `enforce`. `simple` defaults to `enforce`; only the exact value `shadow` opts out.
- `SWITCHYARD_ROUTE_HEALTH_STATE_ROOT`: Host-owned root for the route-health projection `simple` reads (default `<run-store state root>/route-health`, so `SWITCHYARD_RUN_STORE_ROOT` relocates it). The `health` subcommands take `--health-state-root` instead and do not read this variable.
- `SWITCHYARD_PARALLELS_GOLDEN_IMAGE`: Read only by `health identity`, where it supplies the configuration reference behind the public configuration epoch (default `golden-image-unconfigured`). `simple` ignores it and uses the fixed reference `switchyard-simple-direct-v1`.
- `SWITCHYARD_CANARY_REV`: Required by `ops/install-sandbox-canary.sh`; the explicitly accepted full 40-hex commit SHA whose `git archive` snapshot the LaunchAgent runs. Missing or non-hex input fails the install closed.
- `SWITCHYARD_CANARY_DAILY`, `SWITCHYARD_CANARY_STATE_DIR`, `SWITCHYARD_CANARY_DEADLINE_MS`, `SWITCHYARD_CANARY_SANDBOX_EXEC`, `SWITCHYARD_CANARY_INSTALL_TIMEOUT_SECONDS`: Test and operator overrides for the daily canary driver and installer (enable daily dedupe, relocate the state directory, set the bounded deadline, inject the `sandbox-exec` path, or cap each external tool call at up to 60 s; CLI `--force` bypasses daily dedupe). Production defaults are the UTC-day schedule, `~/Library/Application Support/switchyard/sandbox-canary-state`, and a 300 s deadline.
- `SWITCHYARD_TEST_SCRATCH_ROOT`, `SWITCHYARD_HOST_HOME`: Test-only. The first relocates the parent of the hermetic test scratch directory (default `$TMPDIR`); the second is the owner's real home, set by the hermetic environment for the few tests that check host ground truth.
- `SWITCHYARD_TEST_PYTEST_VENV`: Test-only input for the serial Python Quick host suite; points at an existing venv with installed pytest so the real-pytest cases execute without installing packages. Unset, the portable suite checks the checkout-local `.venv`, then the parent directory `.venv`, and skips the host cases when neither is usable; `validate:host` and a contract-gate run that needs the suite refuse before any phase starts, naming this variable, because six executed cases are required.
- `SWITCHYARD_COMPATIBILITY_ROOT`: Test-only. Points the three simple-lane compatibility regressions at an immutable source tree of baseline `5c77335c8bec3f1ff6dddcc4521a3de893de7310`; unset, they archive that baseline from Git history.

## Conventions

- All files self-contained under this directory.
- Secrets in BWS. Never committed. Provider credentials injected into an execution environment are treated as **already compromised**.
- Update `HISTORY.md` alongside every meaningful change. Bug entries cite the files touched (`- files: path/a.py, path/b.ts`).
- Tests verify real behavior — no smoke-only "did it run" checks. Containment invariants are backed by gate tests that exercise the real boundary (the simple-dispatch suites that INV-1 and INV-3 name in `INVARIANTS.md`), not by assertion alone.

## Compatibility and versioning

`package.json` is the authoritative SemVer version source. The compatibility contract covers the documented CLI commands and options, configuration formats, typed dispatch receipts, and persisted run-state formats. During initial `0.y.z` development, incompatible changes and new features increment the minor version; compatible fixes increment the patch version. Assess the version at each accepted checkpoint and prepare one version for a completed, tested milestone intended for use or distribution. Internal refactors preserve this contract.

[CHANGELOG.md](CHANGELOG.md) records noteworthy changes for people. Ongoing work stays under `Unreleased`; an accepted commit alone does not establish a release.
