2. A queue success was premature

Task 51's contract declared npm run lint among its Quick checks. Run 4d72698c-18de-45e7-a816-ff86a3e04f38 reached succeeded, and its events show provider completion, artifact capture, integration and task completion, with no check event. The delivery record later recorded that the worker ran lint and it failed on formatting; the captain fixed formatting and passed lint afterward. Absence of a queue check event alone would not prove the worker never ran a check. The defect is that the queue did not require a passing check receipt for its success claim.

Provider finished→Diff integrated→Queue marked success↛Declared lint passed

The cause is structural: runner/index.mjs:7201–7212 derives task success from the structural integration gate; parseTaskQueue does not parse Quick checks. By contrast, simple/index.mjs:2109–2168 runs its explicit --check list before integration. Thus the two dispatch lanes do not mean the same thing by task success.

Recommended immediate contract fix: represent artifact integration, check state and captain acceptance as separate facts. Missing check evidence is unverified; a known failed check is failed. Neither may produce an accepted-task receipt. Changing only a display string would leave downstream consumers of success=true exposed.

Astra's read-only consultation challenged this recommendation on one point: if existing consumers cannot distinguish integration from acceptance, an additive check field is cosmetic. The implementation must audit queue summaries, exit behavior, checkpoint dependencies and consuming automation before changing the status. A later shared check runner may be useful, but it must meet the owner-approved fresh-clone, hardened-Git, allowlisted-environment and non-login-shell requirements before executing provider-written commands on the host.

3. Failure classification and diagnostics

Exit-zero reports remain unproven as one defect

At HEAD, simple/index.mjs:970–975 calls any otherwise-unclassified unsuccessful provider result provider_exit_nonzero. This can mislabel a success:false, code:0 result. The normal diff/check path starts only after the success branch. Agy's separate exit/verdict contradiction was fixed in R9 and has tests; that fix should not be generalized to other routes. Matching durable receipts for PaperPal, Slabtastic and CipherBlade were not recovered, so their reported shared cause remains a lead.

Fix test: simulate a non-Agy provider that exits zero with no diff and verify the observed exit stays zero, the result is empty_diff or an explicit unconfirmed-completion reason, and it never says provider_exit_nonzero. Keep a nonzero-exit case distinct. Reconcile the actual adapter result shape before changing production branching.

Failed checks have too little safe detail

simple currently stores {index,status} per check (simple/index.mjs:2148–2168). The retained partialWorktree helps salvage, but callers cannot see the closed exit code or signal and often rerun the check. Record only bounded status fields plus the existing exact worktree/check index pointer. Do not persist raw stdout, stderr, command text or provider content.

Caller-facing reasons and progress

The source already has a 30-minute simple deadline validation and route skip classifications, but some callers received an unhelpful envelope or repeated heartbeat text. Test the exact CLI result path for known invalid deadlines, pinned-provider ineligibility, lock conflict and unsafe diff. Surface a closed reason and remedy, and distinguish a heartbeat from a milestone. Keep same-project serialization because it protects one host checkout.
