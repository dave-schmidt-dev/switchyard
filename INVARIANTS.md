# Invariants — switchyard

> System contract. The harvest tool reads `area:` globs to map HISTORY bug entries
> to invariants. Per-project convention is declared in this project's README.
>
> Confirmed by David Schmidt 2026-07-20. switchyard is a **usage-aware dispatcher**
> that spreads coding tasks across subscription-backed agent CLIs (routing on live
> usage from the `gradus` project) and runs each in a disposable sandbox with no
> rights to the Mac host. Threat model: **accident-containment, not adversary defense.**

### INV-1 — Agents have no rights to the Mac host
area: ["src/switchyard/lifecycle/**", "src/switchyard/auth/**"]
gate_test: tests/no-host-rights-vm.test.mjs
threshold: 3
rationale: The whole safety story. No working VM mounts the host filesystem or host credentials — Parallels host-guest sharing is explicitly disabled for every managed VM. Agents operate only on the working VM's own copy of the code, seeded by `git archive` over the tar-transport seam (see `seedProjectWithBackend`), never a host bind mount. A host mount = the agent can nuke the Mac. Authentication never routes through the host: each provider is credentialed once, by a human working **inside the golden VM image** as the non-admin `switchyard` account — an OAuth device flow for the OAuth providers, a guest-keychain API key for Vibe — and no host credential is ever copied in. That authenticated state is baked into the golden image, and every task-time clone inherits it directly: proven empirically by cloning an authenticated probe VM and confirming the clone reports authenticated with no fresh login (see HISTORY.md). No runtime credential-provisioning step exists, so no credential ever crosses the host/guest boundary at dispatch time. Routing is decided **host-side** (the runner reads gradus's snapshot on the host), so the snapshot never enters the guest either — the only inbound signal is the per-task assignment (chosen provider/model + task text), a control input that carries no host credentials or paths and confers no power over the host.

The `ExecutionBackend` seam preserves this boundary across substrates: each backend owns workspace execution and tar transport, while `execArgv(workspaceId, {cwd})` carries no mode or session parameter. Honoring `cwd` is the backend's obligation because `prlctl exec` has no working-directory field and enters a different launchd domain from the Aqua domain required by the provider.

The Parallels gate adds host-side `prlctl list -i` assertions that host-defined sharing is off, plus guest-side mount, clipboard, and C-3 checks. Clipboard isolation is enforced at the point of use rather than inherited from the image: `ExecutionBackend.create()` tears down the guest's `com.parallels.copypaste` Aqua agent on every clone and then re-samples across a settle window, because a Parallels Guest Tools update restores that LaunchAgent plist in the golden image (observed 2026-08-21) and prltoolsd respawns the agent seconds after boot. A clone that is still clipboard-capable fails to create, so dispatch stops instead of handing a provider a guest that reaches the host pasteboard. The C-3 ruleset is guest-side and blocks host identities, the LAN gateway, and the guest subnet while allowing internet and DNS. These guest observations prove the configured guest posture only; they do not claim host isolation, and guest root remains an accepted bypass that the non-admin provider account is required to prevent.

### INV-2 — Code returns to the Mac only through the explicit, reviewed integration step
area: ["src/switchyard/integrate/**"]
gate_test: tests/integration-gate.test.mjs
threshold: 3
rationale: The single door between the sandbox and the host. Agent output reaches real files only via a reviewed apply/merge — never a direct agent write to the host. Bypassing this is how unattended agents would silently corrupt the Mac's copy. A retained review artifact is evidence only of a captured non-empty diff, not success; its absence never upgrades a failed route or rejected integration to success.

### INV-3 — The disposable workspace is wiped at project end, and no working object ever accumulates
area: ["src/switchyard/lifecycle/**", "src/switchyard/runner/**", "ops/switchyard-reaper.sh"]
gate_test: tests/workspace-wipe-vm.test.mjs, tests/parallels-backend.test.mjs, tests/reaper-script.test.mjs
threshold: 3
rationale: The disposable workspace (a Parallels working VM) is the project-code/build-artifact unit; wiping it per project prevents cross-project state bleed and bounds an accident to one project. The Parallels golden image is never a disposable unit. Disposal must hold on the ABNORMAL paths too, so no leaked object accumulates: reclamation parses the exact reserved `switchyard-work-<runId>-<creatorPid>` name and force-destroys only a PROVEN-dead creator PID. A live owner is never reaped, and a VM whose name does not parse is never touched or reported. A normal exit destroys the workspace; a crash is swept; a graceful signal cleans up its own workspace. A standalone launchd reaper (`ops/switchyard-reaper.sh`) applies the same name-parity/PID-liveness check on an hourly timer independent of any active dispatch, so a leak survives even when nothing is currently running. The no-accumulation / reclamation-liveness half is additionally gated by tests/parallels-backend.test.mjs and tests/workspace-wipe-vm.test.mjs. The live VM gate records a skip when Parallels, the stopped golden image, or a shared VM slot is unavailable; this avoids treating infrastructure absence or the Virtualization.framework guest cap as an INV-3 failure. That cap is why VM admission is exactly two slots: Apple's Virtualization.framework allows at most two concurrently running macOS guests per host, so `VM_SLOT_COUNT = 2` mirrors a platform maximum rather than a policy choice and must never be raised. The two lock files live under the home directory, making the pool host-global — one shared pool across every session, project and harness, which is why a live dispatch in one session can starve a VM gate in another. Run-store text dirs under the state root are governed separately.

### INV-4 — A task is dispatched only to a provider with remaining usage, spreading load across funded providers; every dispatch records provider + model + result
area: ["src/switchyard/router/**", "src/switchyard/roster/**", "src/switchyard/ledger/**", "src/switchyard/adapter/**", "src/switchyard/runner/**"]
gate_test: tests/router.test.mjs
threshold: 3
<!-- Retry supplement: only verified provider-scoped signatures become quota_exhausted; an owned working-VM target may be quarantined for one reset-before-reroute retry, while generic/auth/unknown failures remain terminal. -->
rationale: The product's reason to exist. Routing to an exhausted provider (percent_left at/near 0, or before reset_iso) defeats load-spreading and hits the "out of usage" wall switchyard removes. Funded providers use two routing pools in precedence, followed by one absolute-last-resort candidate. (1) Priority-fill: a roster-declared subset of "cheap implementor" providers — Antigravity (both the Gemini and Claude buckets), Copilot, and Cursor's 1st-party (`ac`) bucket — each carry a roster `implementor_priority` rank and are drained, strictly in that rank order, to a hardcoded 0% floor before any better provider is touched AT ALL; headroom is never compared across ranks (rank 1 always wins over rank 2, even holding less headroom), only same-rank ties fall to the tie-break scorer. This is a deliberate policy choice, not the general behavior: these are the cheap/lower-quality lanes David wants exhausted first, not spread alongside the rest. (2) Only once every priority-fill candidate is drained does the router fall back to the original spread behavior among the unranked remainder (Claude, Codex, opencode-go) — favoring the most remaining headroom rather than draining one before touching the next, so a plan still consumes the aggregate capacity of that pool. (3) Cursor's API (`ap`) bucket is reserved as an absolute last resort: it is never pooled with `ac` (each is matched by its own snapshot window id) and is only eligible once both the priority-fill pool AND the unranked spread pool are exhausted, gated by the ordinary 5% floor. (The provider *priority list* Claude>Codex>Agy>Cursor>Vibe>Copilot governs the order adapters are BUILT, not runtime preference.) Recording provider+model+result per task keeps dispatch auditable and feeds the capability-class → provider/model fitness record INV-5 relies on. At the adapter boundary, only verified provider-specific signatures may become `quota_exhausted`; auth, generic transport/rate-limit text, unknown providers, and near misses remain non-quota failures. Generic provider, transient, timeout, launch, and other prose never authorizes a peer-provider retry; only the separate exact quota retry remains enabled. The runner may quarantine only the exact canonical target from an owned working container, reset before one same-task retry, and never spend a second logical task slot. Before an eligible provider execution or orchestrator launch, the runner must complete a sanitized project-local intent receipt; descriptor-invalid and no-provider outcomes do not launch and therefore do not require an intent receipt. The legacy global ledger is a best-effort projection only, with bounded failure classifications.

### INV-5 — A task runs only on a (provider, model) whose capability class meets its RequiredCapability
area: ["src/switchyard/router/**", "src/switchyard/roster/**"]
gate_test: tests/capability-match.test.mjs
threshold: 3
rationale: Providers and models are not interchangeable. A task whose contract leaves an unresolved cross-cutting or irrecoverable decision needs a high-capability route; a fixed procedure can use a low route, while bounded implementation judgment uses standard. Capability is a hard eligibility FILTER applied *before* INV-4's spread selection — a (provider, model) below the task's `RequiredCapability` is not a candidate — and within the chosen harness the model is right-sized to that capability class. Combined with INV-4's spread this reserves strong providers' headroom for tasks that need them. Newly authored queues declare `RequiredCapability`; omission resolves to `standard` only for legacy compatibility. Explicit `high` or `low` requires a non-empty `RequiredCapabilityJustification` and fails before provider dispatch when absent. Review tasks use this same capability ladder without a reviewer-role route. Gemini Antigravity was re-enabled on 2026-08-13 (Gemini 3.7 Flash, `low` → Flash medium-thinking, `standard` → Flash high-thinking, no `high` slot), so it is no longer excluded by disablement — it is excluded by the same receipt rule as any other target: automatically eligible only with current exact promoted `dispatch_qualified` descriptor evidence, which it does not yet hold. Vibe is an enabled native Vibe-harness target carrying GLM-5.2 at two thinking levels: `low` → `zhipu/glm-5.2-low` and `standard` → `zhipu/glm-5.2-high` (enabled 2026-08-31, GLM slots promoted 2026-09-04). Each class holds its own current exact promoted `dispatch_qualified` descriptor evidence (`sha256:bfb64bc…` and `sha256:4f42e879…`), so both are automatically eligible; the retained 2026-09-01 `mistral-medium-3.5` receipt authorizes nothing because no slot references it. Switchyard writes the guest's Vibe model config at dispatch time and fails the task when Vibe reports having run a model other than the routed selector, so a silent local substitution can no longer be recorded as a successful dispatch of the requested model. The slot was labelled GLM-5.2 until 2026-09-01. The claim recorded here until 2026-09-04 — that the entitlement does not exist and every GLM selector resolved to `mistral-medium-3.5` at the provider — is withdrawn: the substitution was local, performed by Vibe's own config loader against a guest carrying no `~/.vibe/config.toml`, and the experiment that produced the claim could not test entitlement at all. The host account is measurably entitled to `zai-glm-5-2`; whether the guest keychain account is the same account is settled by a dispatch canary, not by that experiment. The 2026-08-31 canary failure is therefore unexplained rather than attributed to the label. Description-based classifier entrypoints fail loud and invalid declared values fail closed.

### INV-6 — Run state is durable and race-free, and a project is never left permanently locked
area: ["src/switchyard/run-store/**", "src/switchyard/dispatch/**", "src/switchyard/diagnostics/**", "src/switchyard/runner/**"]
gate_test: tests/run-store.test.mjs
threshold: 3
<!-- Retry supplement: checkpoint transitions are monotonic and atomic; retry state is authoritative over derived run-store projections, status/result overlay it, and resume reconstructs an interrupted target quarantine before selection. -->
rationale: The detached dispatch lifecycle (`launch` → `status` → `result` → `recover`) persists run state to `.logs/switchyard/runs/<runId>/run.json` as the source of truth a crashed or killed worker can be diagnosed and recovered from. It cannot be the *only* one: a worker that dies before its diagnostics sink exists never writes an event at all, so `launch` also wires the child's stderr to a `boot-stderr.log` the worker retains through every pre-provider failure and unlinks synchronously at the adapter boundary (and on a run that reaches no runnable task), and retention keeps a run directory whose only record is a non-empty boot log — the run store is the durability boundary the rest of the reliability contract stands on. Writes are atomic (a unique tmp path per write, never a fixed or shared one, so concurrent writers can't collide on the same rename) and revision-checked; concurrent writers to the same run are serialized through an in-process per-run queue so a losing writer gets an honest `RevisionError` instead of a silent last-write-wins clobber of another writer's data. A fixed-revision write is not enough on its own — two callers that both capture the same base revision before either commits will still drop the loser — so every worker-bootstrap write that can race another one (the terminal state, and each fire-and-forget event callback: `onTaskStart`, `onTaskRouted`, `onResult`, `onCheckpointSaved`) goes through `updateRunWithRetry`, which re-reads and retries against the freshest revision on conflict rather than losing to a same-instant sibling write. Every acquired run lease and project lock is released on every terminal path — success, task failure, and crash — or reclaimed by `recover`, which releases a lock only after proving it is unowned by a run that is still genuinely active (terminal or worker-process-dead), so recovering a stale run can never yank a lock out from under a different, currently-running one. A project must never be blocked from a future `launch` by a run that has already finished or died.

The shared liveness classifier is the only basis for automatic cleanup: `terminal_clean`, `live`, `startup_grace`, `dead`, and `unknown` are explicit outcomes, with malformed, missing, ambiguous, and cleanup-failed evidence retained. The canonical project-lock identity hashes `project:` plus the resolved absolute project path as data, so it is independent of `process.cwd()`; acquisition and held-state checks cover both body-bound historical lock/claim artifacts and the exact pre-`projectPath` cwd-derived filenames. Project-lock recovery reconciles both known run candidates and every lock/claim on disk under the selected state root. Recovery claims are atomically taken by rename before inspection, body-matched, owner/project-record-matched, and ownership-checked so a replacement owner is never deleted or overwritten; temporary atomic-take proofs preserve their original bounded filename identity, remain visible to recovery, and are retained unless their named owner PID is proven dead. A pre-`projectPath` claim is bound only by a matching run record plus its exact canonical or cwd-derived filename identity. A stale lock can be reclaimed without a surviving VM, but only when its run is resolvable and terminal-clean or proven dead. Cleanup-failed locks, claims, and reservations are never automatically removed: status/result expose an exact state-root-bound remediation command, which requires interactive confirmation and rechecks dead-worker liveness plus exact ownership before mutation. Malformed canonical claims block admission until safely reconciled.

Every initialized run reaches a truthful terminal record on normal completion, handled exception, fatal handler, or dead-worker recovery. Terminal finalization is idempotent: a terminal success or failure cannot be overwritten by a later cleanup/lease error or fabricated second fatal classification. Terminal records carry sanitized failure evidence and, when applicable, `terminalizedBy: worker|dead_worker_recovery`; fatal paths use `null` for unknown counts. Cleanup is persisted as pending before teardown, and teardown or ownership-release failure remains explicitly recovery-required rather than being recorded as complete. Caller envelopes preserve the bounded legacy disposition action and add `direction`, whose closed values are `repair_input`, `advance_authorized_fallback`, `recover_and_retry`, `retry_launch`, `wait`, `complete`, and `stop`. `baseDisposition` alone derives it as a pure total function of `(action, reasonCode, diagnosticCode)`; unknown tuples stop. `advance_authorized_fallback` is run-local evidence only and never authorizes, selects, or invokes a route. A terminal lock conflict carries no fresh holder classification and therefore exposes no blocking run or recovery command; only pre-initialization evidence may direct holder-aware waiting or recovery. Cleanup/recovery safety takes precedence, live run/retry progress is reported before ordinary terminal projections, and contract diagnostics remain repairable even when optional checkpoint evidence cannot be loaded; evidence is projected without prose or raw provider output, and insufficient evidence fails closed. Failed recovery claims are retried only with ownership revalidation, so a replacement project-lock owner cannot be deleted or clobbered, while recovery recognizes a legitimate newer owner as a handoff. Terminal summaries add only the closed outcomes `completed_work`, `no_runnable_work`, `failed_work`, `failed_before_work`, `recovered_dead_worker`, or `unknown_failure`.

VM admission persists only closed categories: host permission or sandbox denial, storage/I/O failure, generic admission failure, and ordinary two-slot capacity remain distinct. Raw filesystem errors, paths, and host-derived messages never cross into durable diagnostics.
